## `unexpected:subagent-report-never-delivered` [never returns, stays running]

- **BTC-Gateway** — 3 occurrences (5 dispatches), 2026-09-09T10:20Z → 2026-09-09T13:05Z,
  notion-dev 0.21.1, PR #97.

Five dispatches across two seats — `plan-review` Step 2 twice, `review-and-merge`'s completeness
verifier twice — never emitted a final block. The entry states plainly that this is **not** the
documented zero-byte idle shape: every agent stayed in `running` state and `ListAgents`
repeatedly reported it as "started <1m ago", i.e. restarting from the beginning rather than
going quiet. Each was nudged once per the applicable rule, two of them with an explicit "STOP
investigating and emit the block NOW", and none produced a contract. Partial text captured at
kill time shows each agent still working: *"Now let me verify the plan's claims against the
actual repo."*, *"I'll start by reading the plan."* Second dispatches were tightened — named
line ranges, a ~10-15 call budget, five staged input files, one on a smaller model — and still
did not converge. Two seats lost: `PLAN-REVIEW: degraded`, and `COMPLETENESS: degraded` with all
seven criteria defaulting to `blocked` plus the charges item.

**Disposition: `apply`.** The plugin cannot make a harness deliver a result, but every dispatch
site's failure handling is written against a result that **arrived** — it fails, it is empty, or
it is malformed. All three of those *end*. This one does not end, so no check can fire, the
nudge cannot land (a nudge is answered by an agent that is waiting, not by one that is looping),
and the run waits. Unbounded. That is the defect: the seat is not filling and nothing else will
ever say so.

The entry supplies both halves of the remedy. The **tell** is `ListAgents` reporting the same
agent as "started <1m ago" on repeated checks — decisive, and available without a timer. The
**bound** is the missing control; this harvest reuses the ~15 minutes the checks gate in
`## 5. Merge` already bounds its own waiting by, rather than inventing a number.

The entry's own contrast is preserved in the text, because it is what keeps the rule from
overreaching: in the same run the flow-triage `Explore` scout delivered a full report after one
nudge, and the **configured** code reviewer — not a subagent — completed four rounds normally
and found seven real defects. A live sibling agent is not evidence that this one will deliver.

## `unexpected:subagent-returns-zero-bytes`

- **BTC-Gateway** — 5 dispatches across 3 agents in one run, 2026-09-08T20:55Z →
  2026-09-08T21:09Z, notion-dev 0.21.1.

Every dispatch returned an idle notification with an **empty body**: the scout twice (initial
plus the prescribed nudge), the plan reviewer twice. Then a **control probe** — a
`general-purpose` agent whose entire prompt was *"Reply with exactly the word PONG and nothing
else. Do not use any tools."* — **also returned zero bytes**. Neither named agent appeared in a
subsequent `ListAgents` listing, so both had exited. The run stopped before the build:
flow-triage recovered fully (all seven dimensions scored from the caller's own findings), but
the plan-review seat cannot be self-supplied, and because the same mechanism backs
`local-code-review` and the completeness verifier, the work could have been built and could not
have been merged.

**Disposition: `apply`,** for two things the existing zero-byte handling does not cover.

The **control probe** is the first half. Both silent shapes invite the reading that the prompt
was too long, the rubric too complex, or the task too hard — and each of those readings costs
another full dispatch to disprove. One PONG probe rules out all four in a single call. That is
the entry's own diagnostic, and it is what made this failure attributable to the harness.

The **correlation** is the second, and it is deliberately shipped as a disclosure rather than a
stop. `review-and-merge` already records that a dead reviewer and a dead fallback are not
independent conditions; what was missing is that the *earliest* observation of the mechanism —
the plan-review seat — predicts the merge-gate seats, before the build is spent. Converting that
into a stop rule would be wrong, and this same harvest contains the counterexample:
`unexpected:subagent-report-never-delivered` lost both local seats while the configured reviewer
carried four rounds and the PR merged. So degraded still proceeds; what changes is that the
caller is told what else is likely gone, and can decide before spending the build.

**Change:** `plugins/notion-dev/skills/plan-review/SKILL.md:86` and
`plugins/quick-dev/skills/plan-review/SKILL.md:81`, cross-referenced from both
`review-and-merge` forks.

## `unexpected:rows-mode-filter-ignored`

- **BTC-Gateway** — 2 occurrences on the header plus a third recorded in a recurrence note,
  2026-09-07T17:05Z → 2026-09-08T20:57Z, notion-dev 0.21.1.

A rows-mode structured filter on the id property with `number_equals` returned **5 unrelated
rows** with `has_more: true` — the filter silently ignored rather than rejected, with no error.
Re-issuing the same lookup in **SQL mode with a bound parameter** returned exactly the one
intended row. Three runs, three silent ignores, the same five row ids each time. The entry notes
the live column is named `ID`, which the MCP exposes as `userDefined:ID` — a reserved-name remap
the rows-mode filter path may not be applying.

**Disposition: `apply`.** No correctness was lost on these runs, and the entry says so — but it
also names precisely why that was luck: *a silently-ignored filter is indistinguishable from a
genuine multi-hit*. `fetchTicket` step 1 states its verify-before-trusting rule only for the
DB-scoped `notion-search` fallback, so the query-tool path — the primary — has no such rule at
all. And the project-scoping guardrail in step 2 cannot cover the gap: those five rows carry the
same pinned `staticProperties`, because they are the same project's tickets.

Three for three is a reproducible defect, not an incident, which is what makes the SQL-mode
preference warranted rather than superstitious.

**Change:** `plugins/notion-dev/skills/ticket-system/SKILL.md:296` — the resolved page's
`idProperty` is verified on **every** path; more than one row, or `has_more: true`, is never
resolved by taking the first row; SQL mode with a bound parameter is preferred where available.

- **BTC-Gateway** — 1 occurrence, 2026-09-09T09:00Z, notion-dev 0.21.1.

The prior run's stop report asserted *"WORK PRESERVED AND RESUMABLE: worktree, branch, and an

## Derived — the client logs violate `issue-log`'s own entry contract, six ways

Not a logged signature. Observed by reading the two live logs as artifacts, which is the one
thing a harvest is positioned to do and a writing run is not.

Measured, all present right now:

| Observed in a live client log | Contract it breaks |
|---|---|
| Two sections headed `## retry-exhausted:flow-triage-scout`; two headed `## mcp-unavailable:notion` | Write procedure step 2 — signature is the identity |
| A recurrence note for one signature appended inside a **neighbouring** signature's section | — nothing covers it; step 3 forbids appending at all |
| That signature's own entry reads `Occurrences: 2` for a condition its notes describe **three** times | Step 3 — increment on every repeat |
| A hard-wrapped `RESOLVED` line beginning `## Merged, six of eight AC boxes ticked…` | — nothing covers it; it forges a section boundary |
| Four entries whose `**Kind**` carries their own signature class (`mcp-unavailable`, `quota-exhausted`, `retry-exhausted`, `unexpected`) | `Kind` is exactly one of `failed` / `degraded` / `unexpected` |
| A `quota-exhausted:…` signature, a class not on the closed list, for a condition the previous harvest logged as `mcp-error:…-usage-limit` | Class is drawn from a closed list |

**Disposition: `apply`,** for four of the six. Each is unrepairable after the fact — the log is
append-only by design, and its own best-effort rule says a malformed file is never repaired — so
prevention at the write is the only available fix.

The `Kind`-carrying-the-class row is the one that reveals a mechanism rather than a slip:
**four for four**, every off-list value was that entry's own class. `Kind` and `<class>` are two
closed vocabularies two lines apart in the template, and the runs conflated them. The
`quota-exhausted` class coinage is most plausibly the same conflation running the other way, and
is folded into the same fix rather than counted separately — the closed-list rule and the
`unexpected` fallback are both already stated, so restating them would not be an improvement.

The duplicate-headings row has a second, quieter half: step 2 says "search for a line matching
exactly `## <signature>`" and step 3 says update "that section" — **singular**, with no rule for
what to do when two match. So the procedure is undefined on a log that already contains
duplicates, and successive runs update whichever copy they find, splitting the count across
headings that claim to be one condition.

The recurrence row is a contradiction between two shipped documents: `feedback-harvest` Phase 2
and Phase 8 both contract for "free-form recurrence or correction subsections appended below the
fixed fields", while `issue-log` step 3 says to leave every other byte unchanged. Runs write them
anyway, because a recurrence routinely carries more than a count. Sanctioning them precisely —
in the right section, below the fixed fields, and **still** incrementing `Occurrences` — fixes
the misfiling and the undercount with one rule.

**Change:** `plugins/notion-dev/skills/issue-log/SKILL.md:90` (`Kind` is not the class),
`:124` (no line inside an entry begins with `## `), `:200` (step 3a — duplicate headings resolve
to the last, never a third), `:204` (a materially different condition extends the **subject**
with a kebab-case discriminator — `mcp-unavailable:notion-never-registered` — rather than opening
a second section under the same heading; never a bracketed suffix, since a signature has no
spaces and a space-bearing heading is not recognisable as one) and `:206` (recurrence notes:
placement, depth, and the count).

## Derived — this skill's own reset would have orphaned part of a section it harvested

Not a logged signature. Found while planning Phase 8 against the live logs.

`feedback-harvest` Phase 8 step 2 deletes "from its `##` heading to the line before the next
heading at exactly depth two (`## `), or end of file." The `RESOLVED` note in the row above
begins a line with `## Merged, …` **inside** a section this harvest triaged. A range keyed on
bare `^## ` stops there, deleting the entry's fields and leaving its resolution note behind —
a headless fragment that the next harvest re-reads as an untriaged section with no signature and
no fields. Phase 2's digest range has the same bug, and would have computed a digest over a
truncated section, so the Phase 8 comparison could have matched on a partial read.

**Disposition: `apply`.** The discriminator is free: `issue-log`'s signature grammar guarantees
`## <class>:<subject>` is a single token with a colon and **no spaces**, which prose beginning
`## ` cannot accidentally satisfy. Testing the token instead of the hashes fixes both ranges.

This is the repo-local half of the row above — `issue-log` stops writing such lines, and the
harvest stops mis-parsing the ones already written. Both halves ship, because the existing logs
already contain one and resetting them is this harvest's last step.

**Change:** `.claude/skills/feedback-harvest/SKILL.md:315` (the boundary test, stated once) and
its Phase 2 digest range, with `scripts/verify-feedback-harvest.sh` updated — its previous
assertion pinned the old `exactly depth two` rule and is replaced by five that pin the new one.

## Review findings

The review round on the harvest's own pull request raised two `P1` findings, both against changes
this harvest introduced, and both were right. Recorded here because the archive is the durable
record of what shipped, and what shipped is not quite what the sections above first described.

1. **The bracketed discriminator was self-defeating.** The `issue-log` fix prescribed
   `mcp-unavailable:notion [never registered]` — which violates the signature grammar stated 80
   lines above it (*"`<class>:<subject>` — no spaces"*) and, worse, is unrecognisable to the
   **section-boundary test this same pull request added**. A discriminated entry would have been
   folded into the section above it and could then be deleted under *that* section's disposition,
   losing a condition nobody triaged — the exact harm the boundary fix exists to prevent,
   reintroduced by its sibling. Now a hyphenated subject, the shape `option-missing`'s Kind A
   already uses. Fixed in `edee947`.

2. **Rescuing `PLAN.md` by moving it would have broken resume.** Phase 1.2 decides where to
   resume by finding `PLAN.md` in the worktree and reading its checkboxes, and the stop path
   leaves the worktree intact by design — so moving the file made a stopped superpowers run look
   like a fresh one, re-authoring an existing plan or losing a part-built run's task-level resume
   point, with nothing on the resume path ever restoring the rescued copy. Copying keeps both
   properties. Fixed in `09be3db`.

Both are worth recording rather than quietly amending: they are the same class of defect this
harvest spent twelve fixes on — a rule that is correct in isolation and wrong against the
mechanism next to it — and the second is a fix that would have caused a regression strictly worse
than the client evidence that motivated it.
