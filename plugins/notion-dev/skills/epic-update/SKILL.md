# epic-update

Records a resolved ticket against its Epic container. Invoked by `/notion-dev:ticket` (Phase 8) and `/notion-dev:finalize` (Phase 3) — the two entry points that take a ticket to `Implemented`.

**Args:** `<ticket-id>` (the numeric or logical key of the just-resolved ticket), plus `--non-interactive` when the caller is in that mode.

**Caller-supplied context:** `REVIEW_REPORT` (the review loop's final report, source of the deferred follow-ups) and `REPO_ROOT` (the primary checkout — the caller recorded it before any `cd` into a worktree). `REVIEW_REPORT` can arrive **absent** rather than merely empty — `/notion-dev:finalize`'s post-merge recovery path (its Phase 1 step 2) passes it as absent when it could neither load the persisted report file nor reconstruct anything usable from the PR's review history. Absent is not the same as "no deferred follow-ups": it means this invocation has no way to know whether there were any. Step 2 and step 4 below both treat it accordingly.

**Every step here is best-effort**: a failure logs a warning and continues to the next step. This skill never fails its caller's run — the merge has already landed by the time it is invoked, and epic bookkeeping is not worth losing that.

**1. Resolve the epic.** `fetchTicket(<ticket-id>)` and read `metadata.parentTaskProperty`. Empty (`""`) → **skip steps 2-5 entirely** and return `EPIC-UPDATE: none`. Not an error; most tickets have no epic.

**Before concluding "no epic" from that `""`, determine why it is empty — and record the schema causes.** `fetchTicket` collapses three states into the same `""`: the property is usable and simply unset (the common case), absent from the live DB, or present but not a self-referential Relation. Check the live schema and split them:

- **Usable, unset** → routine. Return `none` silently. This is most tickets and must stay unlogged.
- **Absent** → record `missing-property:parentTaskProperty` per `notion-dev:issue-log`, then return `none`.
- **Present but not a self-referential Relation** → record `wrong-type:parentTaskProperty`, then return `none`.

**This skill is a genuine recording owner for those two causes, not a delegate.** `fetchTicket` records neither (see its step 4a) and the five operations that normally own them — `createTicket`'s parent write, `createEpic`, `setParent`, `listEpicChildren`, `refreshEpicTasks` — are all in steps 2-5, which this branch skips. So without recording here the condition is observed by nobody, even though a resolved ticket just silently lost its epic refresh, its follow-up filing, and its auto-close check. That silence is the failure the issue log exists to prevent, and it is why the routine-vs-schema split above cannot be collapsed back into a single `""` test. Both signatures are capped once/run, so recording here never double-logs with a later operation that reaches the column on the same run. The **return value is unchanged in all three cases** — `EPIC-UPDATE: none` — so no caller's control flow depends on this split. Otherwise the referenced page is a **candidate**, not yet `EPIC_ID` — fetch it (`fetchTicket` on that page id) for its title, Epic name (`metadata.epicProperty`), body, and its own `metadata.parentTaskProperty` / `metadata.epicMarkerProperty`.

**Validate the candidate is actually an epic before mutating it.** Its own `parentTaskProperty` must be empty (sanity check — an epic has no parent) **and** its `epicMarkerProperty` must be `true` — the same predicate `findEpics()`, `getEpicContext` step 2, and `/notion-dev:ticket`'s epic guard apply (see "Epic containers" in `skills/ticket-system/SKILL.md`), so all four agree on what an epic is. There is no children-based leg to this check any more — a freshly created, childless epic validates just as well as a long-lived one. This check matters because `parentTaskProperty` is the same relation Notion's native Sub-items feature uses for ordinary parent/child tickets — the README tells users to enable Sub-items, so a `Parent task` value can point at an ordinary ticket just as easily as at an epic; only the marker tells them apart. `metadata.epicMarkerProperty` reads `false` in all three cases — the box is unchecked, the property is absent from the live DB, or it is present but **not a Checkbox** type — so an unusable marker property (absent *or* wrong-typed, which the "Marker usability rule" in `skills/ticket-system/SKILL.md` requires to behave identically) degrades this check to "not an epic" safely, rather than falling back to any structural guess. This skill reads the marker only through `fetchTicket`, never by querying the property itself, so it records nothing **for the marker** under either unusable cause — `fetchTicket` step 4a already did, on the very call in step 1 above. That non-recording is specific to `epicMarkerProperty`: for `parentTaskProperty` this skill **is** a recording owner (step 1), because `fetchTicket` records nothing for that property and step 1 can return before any operation that would. **If validation fails, do not mutate the referenced page**: treat it exactly like a ticket with no parent at all — skip steps 2-5 entirely and return `EPIC-UPDATE: none`.

Only once validation passes does the candidate become `EPIC_ID` (used by step 1a onward). Also record this ticket's `key` (e.g. `"STO-67"`) from the same `fetchTicket(<ticket-id>)` result — used by step 1a.

Also record `TICKET_ASSIGNEE = metadata.assigneeProperty` from that same `fetchTicket` call — `""` when the ticket has no assignee, the property is absent, or it isn't People-typed. Used by step 2.

**1a. Idempotency check.** Before any mutation, parse `## Resolution Log` from the epic body fetched in step 1 into its `### [<KEY>-<n>] resolved — <datetime>` entries (same parse `getEpicContext` step 5 does — that step number belongs to `getEpicContext`, a different operation in `skills/ticket-system/SKILL.md`, not to this file). If an entry already exists whose `<KEY>-<n>` equals this ticket's `key` (step 1) → a prior invocation already recorded this exact resolution (e.g. `/notion-dev:finalize`'s post-merge recovery path re-invoking `epic-update` after an interrupted run had already appended the log entry in step 5). A ticket can accumulate more than one such entry once `FAILED`-item retries start appending their own (see step 5's ordering note below) — when more than one matches, use the **most recent** (last in document order) as the source of truth for everything below; it reflects the latest known state of this ticket's follow-ups.

Because step 5 (the log entry) now runs *after* step 4 (the close attempt) — see step 4 for why that ordering is safe — a matched entry here means the prior invocation's close attempt already ran to completion one way or the other; there is no crash window between the two left to worry about. What can still be stale is the epic's *live* state since that prior invocation: another ticket under the same epic may have resolved independently in the meantime (its own `/notion-dev:ticket` or `/notion-dev:finalize` run), changing the child list and the close verdict. The marker therefore suppresses only the non-idempotent, per-ticket work, not the state-refreshing work:

- **Do not re-run step 2's filing for `FILED`/`ALREADY_FILED`-equivalent items — there is nothing fresh to attempt for them.** Treat `FILED` and `ALREADY_FILED` as empty at the start of this invocation: nothing has been newly created yet.
- **Repopulate `DROPPED` and `FAILED` from the matched log entry — do not default either to empty.** These two are what `UNFILED` used to conflate, and they behave differently on recovery. Before splitting either line into items, check it for the **unknown sentinel** first: a line whose value begins with the literal token `UNKNOWN` is not a list of items at all — it is step 2's own "no `REVIEW_REPORT` to draw from" marker, serialized by a prior invocation. **`UNKNOWN` records that evidence was missing *at that time*, not that evidence is missing permanently — it must be re-evaluated on every invocation, never treated as settled.** So finding the token here is not license to read it back unconditionally: first check whether `REVIEW_REPORT` is available on **this** invocation (loaded from the persisted report file, or reconstructed from PR history — the same two sources the caller-supplied-context note above describes). If it is, do **not** restore the sentinel — treat this ticket's follow-ups as not yet filed instead: skip straight to step 2 and file `REVIEW_REPORT`'s current deferred follow-ups there through the normal path (the per-follow-up `PROVENANCE` dedup protects against re-filing anything an earlier, unrecorded attempt may already have created), then have step 5 record that the previously-unknown state has now been resolved. This supersedes the matched-entry's `FAILED`-only retry described below — there is no historical `FAILED` list to narrow to when the prior record was `UNKNOWN`, only a full current report. Only when `REVIEW_REPORT` is **also absent** on this invocation — no report then, no report now — is the line read back as the `unknown` value, never split into items; that is the only case left where the sentinel is restored rather than resolved. Skipping this re-evaluation is the exact bug this sentinel exists to close: a sentinel that is simply parroted back forever, invocation after invocation, can never acquire the `FAILED` items it needs to retry, so the epic it blocks never closes. (Separately, a bare explanatory sentence with no recognizable token, e.g. "review report unavailable — filing failures could not be determined", would read to a parser that only special-cases an absent or empty line as a single genuine failed item — which is why the token check, not just presence/absence of REVIEW_REPORT, comes first.) Only when the line does not begin with `UNKNOWN`, or it did but a current `REVIEW_REPORT` resolved it per above, does the rest of this invocation proceed without a sentinel; otherwise, for a line that begins with `UNKNOWN` and stays unresolved, skip the per-item split entirely and carry the sentinel forward as `unknown`:
  - `DROPPED` is a **user decision**: the original run's interactive gate offered File/Drop and the user chose Drop, with a rationale. That decision is permanent and is never retried here. It does **not** block epic closure — a recorded drop is finished work, not outstanding work. Parse it off the matched entry's `**Follow-ups dropped**` line, **or its legacy spelling `**Follow-ups skipped**`** — epics written before this change carry the old wording and must still parse. Treat both spellings identically. (Items split on the entry's separator; absent line or empty entry → `DROPPED = []`; the sentinel per above → `DROPPED = unknown`.)

    **Track which spelling each item came from.** Items parsed from the legacy `**Follow-ups skipped**` line are `LEGACY_SKIPPED`, a subset of `DROPPED`. They are non-blocking exactly like any other drop — the permanent freeze stays fixed — but they are **not** equivalent to one. A `drop` was decided against, with a rationale. A legacy skip was recorded before `0.13.0` under semantics where declining meant the work was *left undone*, and it carries no rationale because the old prompt never asked for one. Closing over such an item silently is how genuine outstanding work disappears; step 4a discloses it instead.

    **Also parse `**Legacy follow-ups closed over**` into `LEGACY_SKIPPED`, unioned with what the legacy-spelling line yielded.** Provenance would otherwise be laundered in one hop: step 5 re-serializes every `DROPPED` item — legacy ones included — onto the **new** `**Follow-ups dropped**` line. So an invocation that retries a `FAILED` item, fails again, does *not* close, and writes a fresh entry leaves the next invocation matching an entry whose only drop line is the new spelling. That invocation would compute `LEGACY_SKIPPED = []`, close, and never fire step 4a — the exact silent close this tracking exists to prevent. Reading step 5's own legacy line back is what makes the provenance survive re-serialization.
  - `FAILED` is a **transient filing failure**: the original run tried to create the follow-up and the `create-task` invocation itself failed (e.g. a Notion outage), not because anyone chose to skip it. Parse it off the matched entry's `**Follow-ups failed to file**` line the same way (absent line or empty entry → `FAILED = []`; the sentinel per above → `FAILED = unknown`). Each real (non-sentinel) item on this line also carries its **original packet identity** — the `<n>` index (or the packet path outright) that step 2 recorded when it first wrote that item's context packet (see step 2's packet note and step 5's log-entry format below). Parse that identity alongside the item's description and carry it forward verbatim; it is part of the item, not a detail to be recomputed.

  Leaving `FAILED` empty by default makes step 4's condition (3) below pass **vacuously**, and that is a real bug, not a harmless one — the same failure mode this split exists to close. A future edit that "simplifies" this back to a single empty default silently reopens it: a post-merge recovery would close an epic over a follow-up nobody has actually retried yet, because the only surviving record — the log entry's own lines — was never consulted. `DROPPED` no longer blocks closure, so defaulting *it* to empty cannot wrongly close an epic; it must still be repopulated, because step 5 re-serializes it and an empty default would silently erase the user's recorded drop decisions from the epic's history.
- **Retry step 2's creation for the `FAILED` items only — except when the sentinel above was resolved rather than restored.** When the matched entry's `FAILED` was a concrete list (not `UNKNOWN`), a filing failure has no reason to stay lost once whatever caused it (an outage, a rate limit, a transient MCP error) has passed — so this invocation re-attempts creation for exactly the items recorded in `FAILED` above, and nothing else. For each: use the packet identity parsed alongside that item above — `$REPO_ROOT/.claude/notion-dev/followup-<KEY>-<id>-<n>.md`, with `<n>` the exact index carried on the log line — **never recompute `<n>` from this item's position within the `FAILED` list itself**: `FAILED` is a filtered subset of the full `REVIEW_REPORT` enumeration step 2 originally indexed against, so the second entry in a two-item `FAILED` retry is not necessarily the second entry overall, and re-deriving the index from local position finds the wrong packet (or none) whenever an earlier item in the original list was `FILED`, `ALREADY_FILED`, or `DROPPED` instead of `FAILED`. The packet at that path was persisted by the original attempt in step 2 *before* it called `create-task`, so it exists regardless of whether that call succeeded. Re-run the same `/notion-dev:create-task` invocation (same derived title, `PROVENANCE`, and `--parent=<EPIC_ID>`) described in step 2 below. The per-follow-up dedup there (title filter + `PROVENANCE` check) is what makes this safe to retry blindly: if the original attempt actually landed in Notion despite being recorded as failed, this retry recognizes it as already filed (moves it to `ALREADY_FILED`) instead of creating a duplicate. An item that succeeds this time moves into this invocation's `FILED`; one that fails again stays in `FAILED`, keeps its packet identity, and is reported again. On this concrete-list branch, this retry is the only filing work this invocation does — `DROPPED` items are not revisited, and no new items from `REVIEW_REPORT` are considered, because this branch, by construction, doesn't have a fresh `REVIEW_REPORT` to draw from (if one were available, the sentinel-resolution case above would have applied instead — this branch is reached only when the matched entry's list was already concrete). The separate, sentinel-was-`UNKNOWN` branch above does the opposite: no historical `FAILED` subset exists to retry, so it runs step 2's full filing pass against the current `REVIEW_REPORT` instead of this narrower retry.
- **Still run step 3** (`refreshEpicTasks` + `listEpicChildren`) **and step 4** (the close check, re-evaluated against the repopulated/retried `DROPPED` and `FAILED` and the *current* child list) — both are idempotent by construction. Re-running them is how bookkeeping that went stale *since* the prior invocation — a sibling resolved afterward, an epic that can close now but couldn't then — gets corrected on this recovery invocation.
- **Run step 5 only when this invocation actually changed something.** On the concrete-list branch: if `FAILED` (as repopulated from the matched entry) was empty — nothing to retry — then step 2 did no work this invocation, and appending another log entry would only duplicate the one already there; skip step 5. If `FAILED` was non-empty, the retry above is real, ticket-creating work (or a re-confirmed failure), and step 5 **does** run to append a fresh entry recording that outcome. On the sentinel-resolution branch, step 5 **always** runs, regardless of what step 2's fresh filing pass produced (even an empty deferred-follow-ups list) — the previously-unknown state has now been resolved to a known one, and that resolution is itself the fact worth recording; skipping the log entry here would leave the sentinel's history silently incomplete. Either way, appending is the same append-only append it always does; a ticket's resolution can legitimately gain more than one log entry when a retry, or a sentinel resolution, happens later.

Return `EPIC-UPDATE: already-recorded`, reporting what actually happened on this path: on the concrete-list branch, fresh filing beyond the `FAILED` retry is suppressed, and the log append is too when nothing was retried; task-list refresh and the close check ran regardless; a `FAILED`-item retry, when one occurred, is reported like any other filing activity. On the sentinel-resolution branch, report step 2's full fresh-filing outcome (`FILED`/`ALREADY_FILED`/`DROPPED`/`FAILED`) exactly as step 2 produced it, not as a retry — the historical `unknown` no longer applies to this invocation's report at all.

**2. File deferred follow-ups.** Source: **only the `FILED` list** from `REVIEW_REPORT` — the same list written to the ticket's `## Merged` **Deferred follow-ups** field. `ABSORBED` items are already merged and `DROPPED` items are already decided; neither is ever filed. Reading any list but `FILED` here reinstates the unbounded ticket growth this split exists to stop.

When `REVIEW_REPORT` is **absent** (not merely a report with an empty deferred-follow-ups list) — the caller could not produce or recover one, per the note above — skip this step entirely: there is no list to file from. Record `FILED = []`, `ALREADY_FILED = []`, and set **both** `DROPPED` and `FAILED` to the sentinel **unknown** rather than `[]` — an empty list asserts "nothing was dropped" (for `DROPPED`) or "nothing failed to file" (for `FAILED`), and this invocation has no basis to assert either. Carry `FAILED = unknown` into step 4 (close check, conditions three and four — `DROPPED` does not participate in the close check at all) and carry **both** into step 5 (log entry). The **unknown** value is not text — it is a distinct sentinel state, and step 5 must serialize it as an explicit, machine-recognizable token rather than as a human sentence, so a later recovery invocation's parser (step 1a) can tell it apart from a real, one-item list (see step 5's log-entry format).

This step is deduplicated **per follow-up**, not just at the whole-invocation level step 1a already covers. Step 1a's log-entry check is a fast path for the fully-completed case; it cannot catch a run that died after this step created a ticket but before step 5 appended the log entry, because the log entry is written *after* this step, not before. So each follow-up must recognize on its own whether it was already filed by a prior, interrupted invocation:

- Call `listEpicChildren(EPIC_ID)` once, before filing anything, to get the epic's current children. (This is separate from step 3's own `listEpicChildren` call below, which re-fetches *after* this step's creates so its list reflects them.)
- For each item, derive its ticket title **deterministically** from the review finding — the same finding text must always produce the same title, verbatim, on every invocation. This derived title is a cheap **filter** for the dedup check below, not the dedup key itself: Notion does not enforce title uniqueness, so an unrelated child can happen to carry the same title, and treating a title match alone as proof would silently associate this run's finding with someone else's pre-existing work. The title is still load-bearing for one thing besides filtering: it is the exact string passed as `--title` to `/notion-dev:create-task` below, which pins it as the ticket's actual stored title — `create-task`'s interviewer is otherwise free to rewrite whatever title it's handed, and the filter below would then be comparing against a title that was never actually stored. If the derivation itself varies run to run (paraphrasing, embedding a timestamp, truncating differently), the filter can spuriously miss a real match regardless of pinning — determinism and pinning are both still required, even though title alone no longer decides the match.
- Also derive `PROVENANCE` for the item, deterministically from the same review finding: `Follow-up-of: <KEY>-<n> · finding-hash: <hex>` — `<KEY>-<n>` is this ticket's own `key` (step 1), and `<hex>` is the first 12 hex characters of a SHA-1 (or equivalent) digest of the finding's raw text, taken *before* any title-shaping. This is the actual dedup key: unlike the title, it ties a follow-up to *this specific resolved ticket and finding*, so two unrelated items that happen to render the same title never collide on it.
- **Already filed** — a child whose title (case-insensitive, prefix-stripped) matches this item's derived title is a **candidate**, not yet a confirmed match. `fetchTicket` that candidate (only title-matching candidates are ever fetched, so cost stays proportional to collisions, not to epic size) and check whether its body's `## Context` section contains this item's exact `PROVENANCE` line. Only when it does is the candidate **already filed** — record it under `ALREADY_FILED` (with the existing child's `id`/`title`/`url`) and move to the next item. A title match whose `## Context` lacks this `PROVENANCE` line (including a pre-existing, unrelated ticket that merely happens to share the title) is **not** a match — fall through to "Not yet filed" below and file it normally: the coincidence was title-only.
- **Not yet filed** — gate creation:
  - **Interactive**: `AskUserQuestion` — **File as ticket** / **Drop (with rationale)**. Default File. The item arriving here has already been triaged `file` upstream, so choosing Drop is not "leave it undone" — it is *"I disagree with that triage; this is a `drop`."* That is a **decision**, and a decision closes work rather than blocking it. The rationale is required and is written into step 5's log entry. Drop → the item goes to `DROPPED`; it is never retried, and it never blocks closure.
  - **Non-interactive**: file it. Nothing is left deferred by choice (a filing attempt can still fail — see below — but that lands in `FAILED`, not `DROPPED`).

For each item actually filed (i.e. not deduped as already-filed, and not user-dropped), write a context packet to `$REPO_ROOT/.claude/notion-dev/followup-<KEY>-<id>-<n>.md` (`<n>` = the item's 1-based position in the **full** `REVIEW_REPORT` enumeration — fixed at this point, for this item, permanently; the same self-ignored directory the ledger lives in, so it never appears in `git status` or contaminates a branch) containing: the resolved ticket's title, body, and URL; the PR URL and `git show --stat <merge-commit>`; the review finding verbatim; and the rationale recorded when it was deferred. Leave the packet in place after the run as a record of what the ticket was generated from.

**`<n>` is part of this item's identity, not a detail to be recomputed later.** Whenever this item's outcome (in particular a `FAILED` entry) is persisted anywhere downstream — the log entry step 5 writes, and the parse a later recovery invocation reads back in step 1a — `<n>` (or the packet path outright) must travel with it verbatim. A retry that only sees the filtered `FAILED` subset of this run's items and re-derives `<n>` from that subset's own position gets the wrong number the moment any earlier item in the original enumeration landed in `FILED`, `ALREADY_FILED`, or `DROPPED` instead — the retry then either finds no packet or loads a different finding's context. See step 1a's retry bullet for the recovery-side half of this rule.

The ticket's own `## Context` section — populated by the interviewer from this packet — should still read naturally to a human: which resolved ticket and which finding this follow-up traces back to. That's for readers, and is not relied on for dedup as prose, since the interviewer is free to paraphrase whatever the packet hands it. The marker itself is pinned via `--provenance` on the `create-task` call below — the direct analogue of `--title` — which folds it into `## Context` verbatim **as part of the same write that creates the ticket**, not as a separate call afterward. Title and `PROVENANCE` are independent safeguards from here on: the title narrows the search to candidates worth fetching, `PROVENANCE` proves which candidate, if any, is the real match.

This atomicity is the whole point and must not be undone by a future edit. Dedup here has already gone through two prior, insufficient fixes — keying on a derived title (rewritable by the interviewer), then pinning the title (not unique, so an unrelated ticket could coincidentally match), then keying on `PROVENANCE` instead. All three attempts still left a window open as long as the marker was written by a call *after* `create-task` returned: a run interrupted between the ticket's creation and that follow-up call left a same-title, unmarked child that the "Already filed" check above correctly refuses to treat as a match — so recovery would file a duplicate. Passing `--provenance` closes that window because the marker is written in the exact same operation that creates the ticket: the two either both exist or neither does, with no crash-window in between. Do not reintroduce a post-creation `appendToSection` of this marker.

Then run:

```
/notion-dev:create-task --non-interactive --context-file=<packet> --epic="<epic name>" --parent=<EPIC_ID> --title="<derived title>" --provenance="<PROVENANCE>" [--assignee=<TICKET_ASSIGNEE>] prompt:<finding title>
```

Include `--assignee=<TICKET_ASSIGNEE>` only when `TICKET_ASSIGNEE` (step 1) is non-empty. When it's empty — the resolved ticket had no assignee — omit the flag entirely and let create-task's own Phase 2.75 `defaultAssignee` resolution decide; that fallback is exactly what Phase 2.75 already does for any caller that doesn't pass `--assignee`, so no special-casing is needed here.

Record `FILED` = `[{ id, title, url }]` for each newly created ticket, `ALREADY_FILED` = `[{ id, title, url }]` for each item deduped against an existing child, `DROPPED` = the items the user chose to drop (each with its rationale), and `FAILED` = the items whose `create-task` invocation itself failed, **each paired with the `<n>` packet identity recorded for it above**. These last two are **not interchangeable**, and must be tracked and reported separately: `DROPPED` is a permanent user decision that **closes the item out** rather than blocking closure (see step 4); `FAILED` is a transient failure that a later invocation retries automatically (see step 1a), and it is specifically `FAILED`'s packet identity that step 5 must serialize onto the log line and step 1a must parse back — `DROPPED` items are never retried, so they need no packet reference. A create-task failure is **non-fatal**: log it, add the item (with its packet identity) to `FAILED` — never to `DROPPED`, which would misrepresent a filing error as a deliberate decision and, per step 1a, permanently stop it from ever being retried — continue. When `REVIEW_REPORT` has no deferred follow-ups, all four lists are empty and this step is a no-op.

**3. Refresh the epic's `## Tasks`.** Invoke `notion-dev:ticket-system` operation `refreshEpicTasks(EPIC_ID)`, then `listEpicChildren(EPIC_ID)` to hold the child list for steps 4 and 5. Do **not** render the task list here — `refreshEpicTasks` owns that format, and duplicating it is how this section drifts from the one `/notion-dev:create-task` writes.

The mirror is refreshed only on resolution, so between resolutions it lags reality; the live view is Notion's Parent task relation column, and the section exists so the epic reads as a coherent document.

**4. Close the epic.** Evaluate against the child list step 3 already fetched — read *after* step 2 filed its follow-ups, so new tickets are in it. Do not re-query.

Close only when **all** of:
1. Every child other than the just-resolved one has a status in the resolved set. This is the sole **live-state** signal among the four — it comes from step 3's fresh `listEpicChildren` call, so it reflects the epic's actual, current state regardless of what any prior invocation did.
2. `FILED` is empty. This is **this-run bookkeeping**, not live state: a ticket this invocation just created moments ago is unresolved by construction (fresh tickets start in `Backlog`), so condition (1) already fails while it's outstanding. Stated explicitly so the intent survives any future change to when the child list is read — but it adds nothing (1) doesn't already cover.

   `ALREADY_FILED` does **not** appear in this condition, and must not be added back to it. Unlike `FILED`, an `ALREADY_FILED` entry is a *pre-existing* child recognized by this run's dedup check (step 2) — condition (1) already evaluates its live status independently, and that status is not guaranteed to still be unresolved: a prior invocation could have created the follow-up and been interrupted before reaching step 5, and that follow-up could then have been completed before this recovery invocation ran. In that case condition (1) correctly sees every child resolved, but treating `ALREADY_FILED` as its own blocking condition would refuse to close anyway — with no guaranteed retry, since nothing about the epic's state changes on a later run to make the stale check pass. The epic would stay open forever with all work done. Condition (1) is the only signal this invocation needs for these tickets; `ALREADY_FILED` reports what step 2 recognized, for the output block, not what should gate closure.
3. `FAILED` is empty — a follow-up whose filing failed is not yet finished, and it is expected to resolve itself: step 1a retries every `FAILED` item on each recovery invocation, so this condition self-heals once the underlying cause (an outage, a transient MCP error) clears, with no user action required. On the recovery path, `FAILED` reflects the **outcome of this invocation's retry** — items that succeeded moved to `FILED`/`ALREADY_FILED` and no longer count here; only items that failed again remain.
4. The deferred-item triage is not the **unknown** sentinel (step 2, when `REVIEW_REPORT` arrived absent). This overlaps condition 3 rather than being disjoint from it: an absent `REVIEW_REPORT` sets `FAILED` to the sentinel, which is not empty, so condition 3 fails as well. The distinction that matters is not *which* condition blocks but *what the operator is told* — condition 3's phrasing promises an automatic retry, which is true only when a filing genuinely failed. Evaluate this condition before reporting, so a run with no report is described as "review report unavailable" rather than as a retry that will never come. An absent `REVIEW_REPORT` must never read as "nothing was filed or failed" — that reading is exactly the bug this condition exists to close off, since it would let a merged-then-interrupted recovery run close an epic over real outstanding work purely because the evidence never reached this invocation.

   **This condition guards one unknown, where a previous revision guarded two.** It formerly checked `SKIPPED` and `FAILED` independently. Now that a drop is a decision rather than an outstanding item, the only thing an absent `REVIEW_REPORT` hides is whether unfiled `file` items exist — a single unknown. The reduction is deliberate, not a simplification of the kind this file elsewhere warns against: it follows from `DROPPED` leaving the blocking set, and it must be reverted if `DROPPED` ever becomes blocking again.

   Record which condition (if any) failed — step 5 states it plainly in that entry's `Next` line. When this condition and condition 3 both fail (the overlap above — an absent `REVIEW_REPORT` fails both), **this condition is the one reported**, because it is the one that describes what actually happened. On the already-recorded path (step 1a matched), this condition still applies whenever the matched entry's sentinel could not be resolved this invocation either. It does **not** apply when step 1a's `FAILED` came from a concrete historical list, or from a sentinel this invocation resolved against a current `REVIEW_REPORT`. The sentinel must never be treated as permanently cleared because a prior invocation once restored it: each invocation re-evaluates it independently in step 1a.

When all four hold, call `updateStatus(EPIC_ID, "implemented")` **now** — before step 5 writes anything, not after. Otherwise leave the epic's status untouched — this includes refusing to close under condition 3 or 4 even when the others all hold. The plugin never moves an epic *out* of a resolved status, and never sets an epic to `In Progress`.

**Why the close happens before the log entry, not after.** The log entry step 5 writes is a permanent historical record — once it says "epic closed," that should already be true, not merely attempted. Evaluating and performing the close here, then having step 5 describe what actually happened, means the log can never assert an outcome the mutation hasn't reached. This ordering costs nothing: `updateStatus` is idempotent, so re-running this step on a later recovery invocation (step 1a) is free. And if step 5 itself then fails to append, nothing operationally important is lost — the close (if it happened) already landed on the epic's actual status, which is the fact every reader (including `/notion-dev:ticket`'s epic guard) checks; re-filing a duplicate follow-up on a later recovery is prevented by step 2's own per-follow-up dedup (title filter + `PROVENANCE` check), not by this log entry. A missing log entry is a gap in the epic's narrative history, never a correctness gap.

Step 2 must run before step 4, or a run that files a follow-up would close the epic that follow-up belongs to.

**4a. Disclose any legacy skips this close passed over.** Run only when step 4 actually closed the epic **and** `LEGACY_SKIPPED` (step 1a) is non-empty.

`postComment(EPIC_ID, …)` with a note naming every `LEGACY_SKIPPED` item verbatim and stating plainly that the epic closed over them: they were declined before `0.13.0`, when declining meant the work was left undone rather than decided against, so each may or may not still matter. Ask the reader to file what still does.

The comment goes on the **epic page**, not the resolved ticket — the epic is what just closed, and it is where someone looking for this initiative's outstanding work will actually be. This is best-effort like the rest of the skill: a failed `postComment` never fails the run, and never reverts the close. If it fails, record it per `notion-dev:issue-log` under the layer-1 `mcp-error:<tool>-<error-class>` vocabulary — **not** `partial:epic-update`, whose registry row scopes it to the `FAILED-TO-FILE` bucket and names `ticket.md` / `finalize.md` as its recorders, neither of which this is.

**5. Append the log entry.** Runs *after* step 4, so the close has already been attempted and its outcome is known — this entry records what happened, it does not predict it. Invoke `appendToSection(EPIC_ID, "Resolution Log", <entry>)`. The entry is a `divider` block followed by:

```
### [<KEY>-<id>] resolved — <YYYY-MM-DD HH:MM UTC>
**Summary** — <2-4 sentences: what was actually done, distilled from the ticket's ## Implementation section and the merge>
**Follow-ups filed** — [<KEY>-69] Backfill historic wallets · <url>    (`FILED` ∪ `ALREADY_FILED`; omit the line when both are empty — this is the first log entry to record this ticket's resolution regardless of which invocation actually created the follow-up ticket)
**Follow-ups dropped** — <item> — <rationale>, …                   (omit the line when DROPPED is empty. When DROPPED is the **unknown** sentinel, write the line as the literal `UNKNOWN — review report unavailable`.)
**Legacy follow-ups closed over** — <item>, …                      (omit the line when LEGACY_SKIPPED is empty. These were declined before `0.13.0` under the old "left undone" semantics and carry no rationale; the epic closed over them and step 4a commented on the epic.)
**Follow-ups failed to file** — <item> · packet:<n>, …                 (omit the line when FAILED is empty. Each item carries its packet identity as ` · packet:<n>` — the exact `<n>` from `followup-<KEY>-<id>-<n>.md` (step 2) — so a later recovery invocation (step 1a) reuses it verbatim instead of recomputing it from a filtered list. When FAILED is the **unknown** sentinel, write the line as the literal `UNKNOWN — review report unavailable, filing failures could not be determined` instead — no items, no packet references. These are transient — a later invocation retries each one automatically, per step 1a.)
**Epic status** — 2 of 3 tasks resolved, or all N tasks resolved — epic closed (only when step 4's `updateStatus` call actually ran this invocation)
**Next** — <the remaining blocker>, or "epic complete" when step 4 closed it, or (when step 4's condition 4 blocked the close, whether or not condition 3 blocked it too — they overlap, and condition 4 is evaluated first) "review report unavailable — epic left open pending manual review", or "follow-up filing failed — will retry automatically on the next invocation" (only when condition 3 blocked the close and condition 4 did not, i.e. a filing genuinely failed against a report that was present)
```

`## Resolution Log` is created on first use by `appendToSection`. Timestamp from `date -u +"%Y-%m-%d %H:%M UTC"`. `Epic status` counts against step 3's child list using the resolved set, and reads `all N tasks resolved — epic closed` only when step 4 actually reached the `updateStatus` mutation — never write "closed" from the close conditions alone if step 4 for any reason did not perform it. On the recovery path (step 1a) when a `FAILED`-item retry ran, this is a **new** entry describing that retry's outcome, appended after the earlier entry for the same ticket — a ticket can legitimately gain more than one `### [<KEY>-<id>] resolved` entry when a retry happens on a later invocation.

**The `UNKNOWN` token is the first thing step 1a's parser checks on either follow-up line — `**Follow-ups dropped**` or its legacy spelling `**Follow-ups skipped**`, and `**Follow-ups failed to file**`, before ever attempting to split it into items.** It exists precisely because a bare human sentence ("review report unavailable — …") is otherwise indistinguishable from a genuine one-item list to a parser that only special-cases an absent or empty line — that ambiguity is what let the sentinel case get misread as a real failed item and, worse, retried against a packet that was never written. The explanation after the token stays for human readers of the Notion page; it is never parsed as content.

## Output block

Return exactly one block for the caller's report:

```
EPIC-UPDATE: none | updated | closed | already-recorded
EPIC: [<KEY>-<n>] <name> · <url>          (omit on `none`)
FILED: <KEY>-69, <KEY>-70                 (or `none`)
ALREADY-FILED: <KEY>-71                   (or `none`)
DROPPED: <one-liner>, …                   (or `none` or `unknown`)
FAILED-TO-FILE: <one-liner>, …            (or `none` or `unknown`)
CHILDREN: <resolved>/<total> resolved
```

**There is deliberately no `degraded` value.** One was documented here previously and no step ever emitted it; both definitions it carried turned out to describe states this skill cannot reach or cannot observe, and no caller ever keyed on it (`/notion-dev:ticket` and `/notion-dev:finalize` branch only on `none` and `already-recorded`). Do not reintroduce it without a step that actually returns it. The three states it was reached for are each already encoded elsewhere:

- **An unusable `parentTaskProperty`** — absent, or present but not a self-referential Relation — is **`none`**. Step 1 collapses it to the same empty `metadata.parentTaskProperty` as a genuinely parentless ticket and returns on that basis; it never reaches the epic-bookkeeping steps at all.
- **An absent `epicProperty`** is not a degradation of this skill, which never writes the Epic select: it only reads `metadata.epicProperty` as the epic's display name in step 1 and passes `--epic="<name>"` to `create-task` in step 2. An absent property costs it a name, not a write, and `fetchTicket` returns `""` for it silently.
- **A failed step 2-5 write** is already covered by this skill being **best-effort throughout** (see above): the failure warns, the run continues, and the outcome surfaces through the `FAILED-TO-FILE` bucket — which the caller logs as `partial:epic-update`. Adding a return value for it would give one event two encodings.

`none` also covers the case where `metadata.parentTaskProperty` resolves to a page that **fails the epic-structure check in step 1** (e.g. an ordinary Notion Sub-items parent, not an epic container) — no mutation is attempted on it, and the report reads exactly as if the ticket had no parent at all. `already-recorded` means step 1a found an existing `## Resolution Log` entry for this ticket. On the concrete-list branch, fresh filing from `REVIEW_REPORT` and (when nothing needed retrying) the log append were skipped because repeating them would duplicate a ticket or a log entry, but step 3 (`refreshEpicTasks`), step 4 (the close check), and a targeted retry of any `FAILED` items still ran — this is what makes the skill safe, and useful, to invoke more than once for the same ticket (e.g. `/notion-dev:finalize`'s post-merge recovery path). On the sentinel-resolution branch — the matched entry's follow-ups line was `UNKNOWN` and a `REVIEW_REPORT` is available this invocation — fresh filing is **not** skipped: step 2 runs its normal filing pass against the current report (see step 1a), and this report's `FILED`/`ALREADY_FILED`/`DROPPED`/`FAILED` reflect that pass directly rather than a retry. `FILED` and `ALREADY_FILED` reflect only what *this invocation* actually did: empty unless a `FAILED`-item retry succeeded (moving it into `FILED`) or was recognized as already landed (`ALREADY_FILED`); `CHILDREN` below always reflects step 3's fresh count. `DROPPED` and `FAILED`, however, are **not** empty by default on this path — both are repopulated (per step 1a) from the matched log entry's `**Follow-ups dropped**` (or its legacy spelling `**Follow-ups skipped**`) / `**Follow-ups failed to file**` lines, then `FAILED` is further updated by this invocation's retry, so `DROPPED` reports the original run's permanent, user-decided drops while `FAILED-TO-FILE` reports whatever is still unfiled after the retry — items that succeeded moved to `FILED`/`ALREADY_FILED` above and no longer appear here. `ALREADY-FILED` reports step 2's (or step 1a's retry's) **per-follow-up** dedup — a follow-up whose deterministic title matched an existing epic child **and** whose `PROVENANCE` line confirmed the match, so nothing new was created — distinct from `FILED` (newly created this run); a recovery run's report must show which follow-ups it actually did the work of creating versus which it correctly recognized as already done.

`DROPPED: unknown` and `FAILED-TO-FILE: unknown` are distinct values from `none`, reported only when `REVIEW_REPORT` arrived absent this run (step 2) and step 1a did not already recover the answer from a historical log entry — either means step 4's fourth close condition is the reason (if any) the epic did not close, and the caller must not read `unknown` as "nothing was filed or failed." A non-`unknown`, non-empty `FAILED-TO-FILE` is expected to shrink or clear on a later invocation without any user action, since step 1a retries it automatically; a non-empty `DROPPED` will not, since it reflects a decision, not a failure — and, unlike the old `SKIPPED`, it is not a reason the epic stayed open.
