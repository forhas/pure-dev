description: Use after a ticket reaches Implemented, from /notion-dev:ticket Phase 8 or /notion-dev:finalize Phase 3, to record the resolution on the ticket's Epic container — file deferred follow-ups, refresh the Epic's task list, append a dated log entry, and close the Epic when everything under it is resolved.

# epic-update

Records a resolved ticket against its Epic container. Invoked by `/notion-dev:ticket` (Phase 8) and `/notion-dev:finalize` (Phase 3) — the two entry points that take a ticket to `Implemented`.

**Args:** `<ticket-id>` (the numeric or logical key of the just-resolved ticket), plus `--non-interactive` when the caller is in that mode.

**Caller-supplied context:** `REVIEW_REPORT` (the review loop's final report, source of the deferred follow-ups) and `REPO_ROOT` (the primary checkout — the caller recorded it before any `cd` into a worktree). `REVIEW_REPORT` can arrive **absent** rather than merely empty — `/notion-dev:finalize`'s post-merge recovery path (its Phase 1 step 2) passes it as absent when it could neither load the persisted report file nor reconstruct anything usable from the PR's review history. Absent is not the same as "no deferred follow-ups": it means this invocation has no way to know whether there were any. Step 2 and step 4 below both treat it accordingly.

**Every step here is best-effort**: a failure logs a warning and continues to the next step. This skill never fails its caller's run — the merge has already landed by the time it is invoked, and epic bookkeeping is not worth losing that.

**1. Resolve the epic.** `fetchTicket(<ticket-id>)` and read `metadata.parentTaskProperty`. Empty (`""`), or the property absent from the live DB → **skip steps 2-5 entirely** and return `EPIC-UPDATE: none`. Not an error; most tickets have no epic. Otherwise the referenced page is a **candidate**, not yet `EPIC_ID` — fetch it (`fetchTicket` on that page id) for its title, Epic name (`metadata.epicProperty`), body, and its own `metadata.parentTaskProperty` / `metadata.epicMarkerProperty`.

**Validate the candidate is actually an epic before mutating it.** Its own `parentTaskProperty` must be empty (sanity check — an epic has no parent) **and** its `epicMarkerProperty` must be `true` — the same predicate `findEpics()`, `getEpicContext` step 2, and `/notion-dev:ticket`'s epic guard apply (see "Epic containers" in `skills/ticket-system/SKILL.md`), so all four agree on what an epic is. There is no children-based leg to this check any more — a freshly created, childless epic validates just as well as a long-lived one. This check matters because `parentTaskProperty` is the same relation Notion's native Sub-items feature uses for ordinary parent/child tickets — the README tells users to enable Sub-items, so a `Parent task` value can point at an ordinary ticket just as easily as at an epic; only the marker tells them apart. `metadata.epicMarkerProperty` reads `false` whether the box is unchecked or `epicMarkerProperty` is absent from the live DB entirely, so an absent marker property degrades this check to "not an epic" safely, rather than falling back to any structural guess. **If validation fails, do not mutate the referenced page**: treat it exactly like a ticket with no parent at all — skip steps 2-5 entirely and return `EPIC-UPDATE: none`.

Only once validation passes does the candidate become `EPIC_ID` (used by step 1a onward). Also record this ticket's `key` (e.g. `"STO-67"`) from the same `fetchTicket(<ticket-id>)` result — used by step 1a.

Also record `TICKET_ASSIGNEE = metadata.assigneeProperty` from that same `fetchTicket` call — `""` when the ticket has no assignee, the property is absent, or it isn't People-typed. Used by step 2.

**1a. Idempotency check.** Before any mutation, parse `## Resolution Log` from the epic body fetched in step 1 into its `### [<KEY>-<n>] resolved — <datetime>` entries (same parse `getEpicContext` step 5 does — that step number belongs to `getEpicContext`, a different operation in `skills/ticket-system/SKILL.md`, not to this file). If an entry already exists whose `<KEY>-<n>` equals this ticket's `key` (step 1) → a prior invocation already recorded this exact resolution (e.g. `/notion-dev:finalize`'s post-merge recovery path re-invoking `epic-update` after an interrupted run had already appended the log entry in step 5). A ticket can accumulate more than one such entry once `FAILED`-item retries start appending their own (see step 5's ordering note below) — when more than one matches, use the **most recent** (last in document order) as the source of truth for everything below; it reflects the latest known state of this ticket's follow-ups.

Because step 5 (the log entry) now runs *after* step 4 (the close attempt) — see step 4 for why that ordering is safe — a matched entry here means the prior invocation's close attempt already ran to completion one way or the other; there is no crash window between the two left to worry about. What can still be stale is the epic's *live* state since that prior invocation: another ticket under the same epic may have resolved independently in the meantime (its own `/notion-dev:ticket` or `/notion-dev:finalize` run), changing the child list and the close verdict. The marker therefore suppresses only the non-idempotent, per-ticket work, not the state-refreshing work:

- **Do not re-run step 2's filing for `FILED`/`ALREADY_FILED`-equivalent items — there is nothing fresh to attempt for them.** Treat `FILED` and `ALREADY_FILED` as empty at the start of this invocation: nothing has been newly created yet.
- **Repopulate `SKIPPED` and `FAILED` from the matched log entry — do not default either to empty.** These two are what `UNFILED` used to conflate, and they behave differently on recovery. Before splitting either line into items, check it for the **unknown sentinel** first: a line whose value begins with the literal token `UNKNOWN` is not a list of items at all — it is step 2's own "no `REVIEW_REPORT` to draw from" marker, serialized by a prior invocation, and must be read back as the `unknown` value, never split into items. Skipping this check is the exact bug this sentinel exists to close: a bare explanatory sentence with no recognizable token (e.g. "review report unavailable — filing failures could not be determined") reads, to a parser that only special-cases an absent or empty line, as a single genuine failed item — and `FAILED`'s retry below would then try to file it against a context packet that was never written, because no real finding ever produced one. Only when the line does not begin with `UNKNOWN` does the per-item split apply:
  - `SKIPPED` is a **user decision**: the original run's interactive gate offered File/Skip and the user chose Skip. That decision is permanent and is never retried here. Parse it off the matched entry's `**Follow-ups skipped**` line (its items, split on the entry's separator; absent line or empty entry → `SKIPPED = []`; the sentinel per above → `SKIPPED = unknown`) and carry it into step 4 unchanged.
  - `FAILED` is a **transient filing failure**: the original run tried to create the follow-up and the `create-task` invocation itself failed (e.g. a Notion outage), not because anyone chose to skip it. Parse it off the matched entry's `**Follow-ups failed to file**` line the same way (absent line or empty entry → `FAILED = []`; the sentinel per above → `FAILED = unknown`). Each real (non-sentinel) item on this line also carries its **original packet identity** — the `<n>` index (or the packet path outright) that step 2 recorded when it first wrote that item's context packet (see step 2's packet note and step 5's log-entry format below). Parse that identity alongside the item's description and carry it forward verbatim; it is part of the item, not a detail to be recomputed.

  Leaving either empty by default makes step 4's condition (3) or (4) below pass **vacuously**, and that is a real bug, not a harmless one — the same failure mode this split exists to close. A future edit that "simplifies" this back to a single empty default silently reopens it: a post-merge recovery would close an epic over work everyone agreed to leave outstanding (the `SKIPPED` case), or over a follow-up nobody has actually retried yet (the `FAILED` case), because the only surviving record — the log entry's own lines — was never consulted.
- **Retry step 2's creation for the `FAILED` items only.** Unlike `SKIPPED`, a filing failure has no reason to stay lost once whatever caused it (an outage, a rate limit, a transient MCP error) has passed — so this invocation re-attempts creation for exactly the items recorded in `FAILED` above, and nothing else. For each: use the packet identity parsed alongside that item above — `$REPO_ROOT/.claude/notion-dev/followup-<KEY>-<id>-<n>.md`, with `<n>` the exact index carried on the log line — **never recompute `<n>` from this item's position within the `FAILED` list itself**: `FAILED` is a filtered subset of the full `REVIEW_REPORT` enumeration step 2 originally indexed against, so the second entry in a two-item `FAILED` retry is not necessarily the second entry overall, and re-deriving the index from local position finds the wrong packet (or none) whenever an earlier item in the original list was `FILED`, `ALREADY_FILED`, or `SKIPPED` instead of `FAILED`. The packet at that path was persisted by the original attempt in step 2 *before* it called `create-task`, so it exists regardless of whether that call succeeded. Re-run the same `/notion-dev:create-task` invocation (same derived title, `PROVENANCE`, and `--parent=<EPIC_ID>`) described in step 2 below. The per-follow-up dedup there (title filter + `PROVENANCE` check) is what makes this safe to retry blindly: if the original attempt actually landed in Notion despite being recorded as failed, this retry recognizes it as already filed (moves it to `ALREADY_FILED`) instead of creating a duplicate. An item that succeeds this time moves into this invocation's `FILED`; one that fails again stays in `FAILED`, keeps its packet identity, and is reported again. This retry is the only filing work this invocation does — `SKIPPED` items are not revisited, and no new items from `REVIEW_REPORT` are considered (this path doesn't have a fresh `REVIEW_REPORT` to draw from; see step 2's own absent-report handling for that separate case).
- **Still run step 3** (`refreshEpicTasks` + `listEpicChildren`) **and step 4** (the close check, re-evaluated against the repopulated/retried `SKIPPED` and `FAILED` and the *current* child list) — both are idempotent by construction. Re-running them is how bookkeeping that went stale *since* the prior invocation — a sibling resolved afterward, an epic that can close now but couldn't then — gets corrected on this recovery invocation.
- **Run step 5 only when the retry changed anything.** If `FAILED` (as repopulated from the matched entry) was empty — nothing to retry — then step 2 did no work this invocation, and appending another log entry would only duplicate the one already there; skip step 5. If `FAILED` was non-empty, the retry above is real, ticket-creating work (or a re-confirmed failure), and step 5 **does** run to append a fresh entry recording that outcome — the same append-only append it always does; a ticket's resolution can legitimately gain more than one log entry when a retry happens later.

Return `EPIC-UPDATE: already-recorded`, reporting what actually happened on this path: fresh filing (beyond the `FAILED` retry) and, when nothing was retried, the log append are suppressed; task-list refresh and the close check ran; a `FAILED`-item retry, when one occurred, is reported like any other filing activity.

**2. File deferred follow-ups.** Source: `REVIEW_REPORT`'s deferred follow-ups — the same list written to the ticket's `## Merged` section.

When `REVIEW_REPORT` is **absent** (not merely a report with an empty deferred-follow-ups list) — the caller could not produce or recover one, per the note above — skip this step entirely: there is no list to file from. Record `FILED = []`, `ALREADY_FILED = []`, and set **both** `SKIPPED` and `FAILED` to the sentinel **unknown** rather than `[]` — an empty list asserts "nothing was left outstanding" (for `SKIPPED`) or "nothing failed to file" (for `FAILED`), and this invocation has no basis to assert either. Carry `SKIPPED = unknown` and `FAILED = unknown` into step 4 (close check, conditions three through five) and step 5 (log entry). The **unknown** value is not text — it is a distinct sentinel state, and step 5 must serialize it as an explicit, machine-recognizable token rather than as a human sentence, so a later recovery invocation's parser (step 1a) can tell it apart from a real, one-item list (see step 5's log-entry format).

This step is deduplicated **per follow-up**, not just at the whole-invocation level step 1a already covers. Step 1a's log-entry check is a fast path for the fully-completed case; it cannot catch a run that died after this step created a ticket but before step 5 appended the log entry, because the log entry is written *after* this step, not before. So each follow-up must recognize on its own whether it was already filed by a prior, interrupted invocation:

- Call `listEpicChildren(EPIC_ID)` once, before filing anything, to get the epic's current children. (This is separate from step 3's own `listEpicChildren` call below, which re-fetches *after* this step's creates so its list reflects them.)
- For each item, derive its ticket title **deterministically** from the review finding — the same finding text must always produce the same title, verbatim, on every invocation. This derived title is a cheap **filter** for the dedup check below, not the dedup key itself: Notion does not enforce title uniqueness, so an unrelated child can happen to carry the same title, and treating a title match alone as proof would silently associate this run's finding with someone else's pre-existing work. The title is still load-bearing for one thing besides filtering: it is the exact string passed as `--title` to `/notion-dev:create-task` below, which pins it as the ticket's actual stored title — `create-task`'s interviewer is otherwise free to rewrite whatever title it's handed, and the filter below would then be comparing against a title that was never actually stored. If the derivation itself varies run to run (paraphrasing, embedding a timestamp, truncating differently), the filter can spuriously miss a real match regardless of pinning — determinism and pinning are both still required, even though title alone no longer decides the match.
- Also derive `PROVENANCE` for the item, deterministically from the same review finding: `Follow-up-of: <KEY>-<n> · finding-hash: <hex>` — `<KEY>-<n>` is this ticket's own `key` (step 1), and `<hex>` is the first 12 hex characters of a SHA-1 (or equivalent) digest of the finding's raw text, taken *before* any title-shaping. This is the actual dedup key: unlike the title, it ties a follow-up to *this specific resolved ticket and finding*, so two unrelated items that happen to render the same title never collide on it.
- **Already filed** — a child whose title (case-insensitive, prefix-stripped) matches this item's derived title is a **candidate**, not yet a confirmed match. `fetchTicket` that candidate (only title-matching candidates are ever fetched, so cost stays proportional to collisions, not to epic size) and check whether its body's `## Context` section contains this item's exact `PROVENANCE` line. Only when it does is the candidate **already filed** — record it under `ALREADY_FILED` (with the existing child's `id`/`title`/`url`) and move to the next item. A title match whose `## Context` lacks this `PROVENANCE` line (including a pre-existing, unrelated ticket that merely happens to share the title) is **not** a match — fall through to "Not yet filed" below and file it normally: the coincidence was title-only.
- **Not yet filed** — gate creation:
  - **Interactive**: `AskUserQuestion` — **File as ticket** / **Skip**. Default File. Skip → the item goes to `SKIPPED`, a user decision — permanent, and never retried by a later invocation.
  - **Non-interactive**: file it. Nothing is left deferred by choice (a filing attempt can still fail — see below — but that lands in `FAILED`, not `SKIPPED`).

For each item actually filed (i.e. not deduped as already-filed, and not user-skipped), write a context packet to `$REPO_ROOT/.claude/notion-dev/followup-<KEY>-<id>-<n>.md` (`<n>` = the item's 1-based position in the **full** `REVIEW_REPORT` enumeration — fixed at this point, for this item, permanently; the same self-ignored directory the ledger lives in, so it never appears in `git status` or contaminates a branch) containing: the resolved ticket's title, body, and URL; the PR URL and `git show --stat <merge-commit>`; the review finding verbatim; and the rationale recorded when it was deferred. Leave the packet in place after the run as a record of what the ticket was generated from.

**`<n>` is part of this item's identity, not a detail to be recomputed later.** Whenever this item's outcome (in particular a `FAILED` entry) is persisted anywhere downstream — the log entry step 5 writes, and the parse a later recovery invocation reads back in step 1a — `<n>` (or the packet path outright) must travel with it verbatim. A retry that only sees the filtered `FAILED` subset of this run's items and re-derives `<n>` from that subset's own position gets the wrong number the moment any earlier item in the original enumeration landed in `FILED`, `ALREADY_FILED`, or `SKIPPED` instead — the retry then either finds no packet or loads a different finding's context. See step 1a's retry bullet for the recovery-side half of this rule.

The ticket's own `## Context` section — populated by the interviewer from this packet — should still read naturally to a human: which resolved ticket and which finding this follow-up traces back to. That's for readers, and is not relied on for dedup as prose, since the interviewer is free to paraphrase whatever the packet hands it. The marker itself is pinned via `--provenance` on the `create-task` call below — the direct analogue of `--title` — which folds it into `## Context` verbatim **as part of the same write that creates the ticket**, not as a separate call afterward. Title and `PROVENANCE` are independent safeguards from here on: the title narrows the search to candidates worth fetching, `PROVENANCE` proves which candidate, if any, is the real match.

This atomicity is the whole point and must not be undone by a future edit. Dedup here has already gone through two prior, insufficient fixes — keying on a derived title (rewritable by the interviewer), then pinning the title (not unique, so an unrelated ticket could coincidentally match), then keying on `PROVENANCE` instead. All three attempts still left a window open as long as the marker was written by a call *after* `create-task` returned: a run interrupted between the ticket's creation and that follow-up call left a same-title, unmarked child that the "Already filed" check above correctly refuses to treat as a match — so recovery would file a duplicate. Passing `--provenance` closes that window because the marker is written in the exact same operation that creates the ticket: the two either both exist or neither does, with no crash-window in between. Do not reintroduce a post-creation `appendToSection` of this marker.

Then run:

```
/notion-dev:create-task --non-interactive --context-file=<packet> --epic="<epic name>" --parent=<EPIC_ID> --title="<derived title>" --provenance="<PROVENANCE>" [--assignee=<TICKET_ASSIGNEE>] prompt:<finding title>
```

Include `--assignee=<TICKET_ASSIGNEE>` only when `TICKET_ASSIGNEE` (step 1) is non-empty. When it's empty — the resolved ticket had no assignee — omit the flag entirely and let create-task's own Phase 2.75 `defaultAssignee` resolution decide; that fallback is exactly what Phase 2.75 already does for any caller that doesn't pass `--assignee`, so no special-casing is needed here.

Record `FILED` = `[{ id, title, url }]` for each newly created ticket, `ALREADY_FILED` = `[{ id, title, url }]` for each item deduped against an existing child, `SKIPPED` = the items the user chose to skip, and `FAILED` = the items whose `create-task` invocation itself failed, **each paired with the `<n>` packet identity recorded for it above**. These last two are **not interchangeable**, and must be tracked and reported separately: `SKIPPED` is a permanent user decision that keeps blocking closure indefinitely (see step 4); `FAILED` is a transient failure that a later invocation retries automatically (see step 1a), and it is specifically `FAILED`'s packet identity that step 5 must serialize onto the log line and step 1a must parse back — `SKIPPED` items are never retried, so they need no packet reference. A create-task failure is **non-fatal**: log it, add the item (with its packet identity) to `FAILED` — never to `SKIPPED`, which would misrepresent a filing error as a deliberate choice and, per step 1a, permanently stop it from ever being retried — continue. When `REVIEW_REPORT` has no deferred follow-ups, all four lists are empty and this step is a no-op.

**3. Refresh the epic's `## Tasks`.** Invoke `notion-dev:ticket-system` operation `refreshEpicTasks(EPIC_ID)`, then `listEpicChildren(EPIC_ID)` to hold the child list for steps 4 and 5. Do **not** render the task list here — `refreshEpicTasks` owns that format, and duplicating it is how this section drifts from the one `/notion-dev:create-task` writes.

The mirror is refreshed only on resolution, so between resolutions it lags reality; the live view is Notion's Parent task relation column, and the section exists so the epic reads as a coherent document.

**4. Close the epic.** Evaluate against the child list step 3 already fetched — read *after* step 2 filed its follow-ups, so new tickets are in it. Do not re-query.

Close only when **all** of:
1. Every child other than the just-resolved one has a status in the resolved set. This is the sole **live-state** signal among the five — it comes from step 3's fresh `listEpicChildren` call, so it reflects the epic's actual, current state regardless of what any prior invocation did.
2. `FILED` is empty. This is **this-run bookkeeping**, not live state: a ticket this invocation just created moments ago is unresolved by construction (fresh tickets start in `Backlog`), so condition (1) already fails while it's outstanding. Stated explicitly so the intent survives any future change to when the child list is read — but it adds nothing (1) doesn't already cover.

   `ALREADY_FILED` does **not** appear in this condition, and must not be added back to it. Unlike `FILED`, an `ALREADY_FILED` entry is a *pre-existing* child recognized by this run's dedup check (step 2) — condition (1) already evaluates its live status independently, and that status is not guaranteed to still be unresolved: a prior invocation could have created the follow-up and been interrupted before reaching step 5, and that follow-up could then have been completed before this recovery invocation ran. In that case condition (1) correctly sees every child resolved, but treating `ALREADY_FILED` as its own blocking condition would refuse to close anyway — with no guaranteed retry, since nothing about the epic's state changes on a later run to make the stale check pass. The epic would stay open forever with all work done. Condition (1) is the only signal this invocation needs for these tickets; `ALREADY_FILED` reports what step 2 recognized, for the output block, not what should gate closure.
3. `SKIPPED` is empty — a known, user-declined follow-up means the work was deliberately left outstanding, and that decision keeps blocking closure until someone files it manually. On the recovery path (step 1a), `SKIPPED` is the set repopulated from the matched log entry's `**Follow-ups skipped**` line, not an empty default — see step 1a for why that read is mandatory. Unlike condition 4 below, nothing about this invocation retries a `SKIPPED` item — it stays blocking until a human acts.
4. `FAILED` is empty — a follow-up whose filing failed is not yet finished, but unlike `SKIPPED` it is expected to resolve itself: step 1a retries every `FAILED` item on each recovery invocation, so this condition self-heals once the underlying cause (an outage, a transient MCP error) clears, with no user action required. On the recovery path, `FAILED` reflects the **outcome of this invocation's retry** — items that succeeded moved to `FILED`/`ALREADY_FILED` and no longer count here; only items that failed again remain.
5. Neither `SKIPPED` nor `FAILED` is the **unknown** sentinel (step 2, when `REVIEW_REPORT` arrived absent). This is a distinct failure mode from conditions 3 and 4, not a rephrasing of them: those fail when there is a *known* outstanding item; this condition fails when there is *no way to know* whether one exists, for either category. An absent `REVIEW_REPORT` must never read as "nothing was deferred or failed" — that reading is exactly the bug this condition exists to close off, since it would let a merged-then-interrupted recovery run close an epic over real outstanding work purely because the evidence of it never reached this invocation. Record which condition (if any) failed — step 5 states it plainly in that entry's `Next` line (e.g. "review report unavailable — epic left open pending manual review" for condition 5, versus the generic remaining-blocker phrasing for condition 1, or a retry-pending phrasing for condition 4). This condition does not apply on the already-recorded path (step 1a matched): there, both `SKIPPED` and `FAILED` are known from the historical log entry (and `FAILED` further refined by this invocation's retry), not from this run's `REVIEW_REPORT`, so neither is ever the unknown sentinel on that path.

When all five hold, call `updateStatus(EPIC_ID, "implemented")` **now** — before step 5 writes anything, not after. Otherwise leave the epic's status untouched — this includes refusing to close under condition 4 or 5 even when the others all hold. The plugin never moves an epic *out* of a resolved status, and never sets an epic to `In Progress`.

**Why the close happens before the log entry, not after.** The log entry step 5 writes is a permanent historical record — once it says "epic closed," that should already be true, not merely attempted. Evaluating and performing the close here, then having step 5 describe what actually happened, means the log can never assert an outcome the mutation hasn't reached. This ordering costs nothing: `updateStatus` is idempotent, so re-running this step on a later recovery invocation (step 1a) is free. And if step 5 itself then fails to append, nothing operationally important is lost — the close (if it happened) already landed on the epic's actual status, which is the fact every reader (including `/notion-dev:ticket`'s epic guard) checks; re-filing a duplicate follow-up on a later recovery is prevented by step 2's own per-follow-up dedup (title filter + `PROVENANCE` check), not by this log entry. A missing log entry is a gap in the epic's narrative history, never a correctness gap.

Step 2 must run before step 4, or a run that files a follow-up would close the epic that follow-up belongs to.

**5. Append the log entry.** Runs *after* step 4, so the close has already been attempted and its outcome is known — this entry records what happened, it does not predict it. Invoke `appendToSection(EPIC_ID, "Resolution Log", <entry>)`. The entry is a `divider` block followed by:

```
### [<KEY>-<id>] resolved — <YYYY-MM-DD HH:MM UTC>
**Summary** — <2-4 sentences: what was actually done, distilled from the ticket's ## Implementation section and the merge>
**Follow-ups filed** — [<KEY>-69] Backfill historic wallets · <url>    (`FILED` ∪ `ALREADY_FILED`; omit the line when both are empty — this is the first log entry to record this ticket's resolution regardless of which invocation actually created the follow-up ticket)
**Follow-ups skipped** — <item>, …                                     (omit the line when SKIPPED is empty. When SKIPPED is the **unknown** sentinel, write the line as the literal `UNKNOWN — review report unavailable, user-skip decisions could not be determined` instead of any item list. These are permanent — the user chose Skip and no invocation retries them.)
**Follow-ups failed to file** — <item> · packet:<n>, …                 (omit the line when FAILED is empty. Each item carries its packet identity as ` · packet:<n>` — the exact `<n>` from `followup-<KEY>-<id>-<n>.md` (step 2) — so a later recovery invocation (step 1a) reuses it verbatim instead of recomputing it from a filtered list. When FAILED is the **unknown** sentinel, write the line as the literal `UNKNOWN — review report unavailable, filing failures could not be determined` instead — no items, no packet references. These are transient — a later invocation retries each one automatically, per step 1a.)
**Epic status** — 2 of 3 tasks resolved, or all N tasks resolved — epic closed (only when step 4's `updateStatus` call actually ran this invocation)
**Next** — <the remaining blocker>, or "epic complete" when step 4 closed it, or "follow-up filing failed — will retry automatically on the next invocation" (when condition 4 was what blocked the close), or (when step 4's condition 5 was what blocked the close) "review report unavailable — epic left open pending manual review"
```

`## Resolution Log` is created on first use by `appendToSection`. Timestamp from `date -u +"%Y-%m-%d %H:%M UTC"`. `Epic status` counts against step 3's child list using the resolved set, and reads `all N tasks resolved — epic closed` only when step 4 actually reached the `updateStatus` mutation — never write "closed" from the close conditions alone if step 4 for any reason did not perform it. On the recovery path (step 1a) when a `FAILED`-item retry ran, this is a **new** entry describing that retry's outcome, appended after the earlier entry for the same ticket — a ticket can legitimately gain more than one `### [<KEY>-<id>] resolved` entry when a retry happens on a later invocation.

**The `UNKNOWN` token is the first thing step 1a's parser checks on either follow-up line, before ever attempting to split it into items.** It exists precisely because a bare human sentence ("review report unavailable — …") is otherwise indistinguishable from a genuine one-item list to a parser that only special-cases an absent or empty line — that ambiguity is what let the sentinel case get misread as a real failed item and, worse, retried against a packet that was never written. The explanation after the token stays for human readers of the Notion page; it is never parsed as content.

## Output block

Return exactly one block for the caller's report:

```
EPIC-UPDATE: none | updated | closed | degraded | already-recorded
EPIC: [<KEY>-<n>] <name> · <url>          (omit on `none`)
FILED: <KEY>-69, <KEY>-70                 (or `none`)
ALREADY-FILED: <KEY>-71                   (or `none`)
SKIPPED: <one-liner>, …                   (or `none` or `unknown`)
FAILED-TO-FILE: <one-liner>, …            (or `none` or `unknown`)
CHILDREN: <resolved>/<total> resolved
```

`degraded` means the DB lacks `epicProperty` or `parentTaskProperty`, so epic containers are unavailable — distinct from `none`, which means this ticket simply has no epic. `none` also covers the case where `metadata.parentTaskProperty` resolves to a page that **fails the epic-structure check in step 1** (e.g. an ordinary Notion Sub-items parent, not an epic container) — no mutation is attempted on it, and the report reads exactly as if the ticket had no parent at all. `already-recorded` means step 1a found an existing `## Resolution Log` entry for this ticket: fresh filing from `REVIEW_REPORT` and (when nothing needed retrying) the log append were skipped because repeating them would duplicate a ticket or a log entry, but step 3 (`refreshEpicTasks`), step 4 (the close check), and a targeted retry of any `FAILED` items still ran — this is what makes the skill safe, and useful, to invoke more than once for the same ticket (e.g. `/notion-dev:finalize`'s post-merge recovery path). `FILED` and `ALREADY_FILED` reflect only what *this invocation* actually did: empty unless a `FAILED`-item retry succeeded (moving it into `FILED`) or was recognized as already landed (`ALREADY_FILED`); `CHILDREN` below always reflects step 3's fresh count. `SKIPPED` and `FAILED`, however, are **not** empty by default on this path — both are repopulated (per step 1a) from the matched log entry's `**Follow-ups skipped**` / `**Follow-ups failed to file**` lines, then `FAILED` is further updated by this invocation's retry, so `SKIPPED` reports the original run's permanent, user-declined items while `FAILED-TO-FILE` reports whatever is still unfiled after the retry — items that succeeded moved to `FILED`/`ALREADY_FILED` above and no longer appear here. `ALREADY-FILED` reports step 2's (or step 1a's retry's) **per-follow-up** dedup — a follow-up whose deterministic title matched an existing epic child **and** whose `PROVENANCE` line confirmed the match, so nothing new was created — distinct from `FILED` (newly created this run); a recovery run's report must show which follow-ups it actually did the work of creating versus which it correctly recognized as already done.

`SKIPPED: unknown` and `FAILED-TO-FILE: unknown` are distinct values from `none`, reported only when `REVIEW_REPORT` arrived absent this run (step 2) and step 1a did not already recover the answer from a historical log entry — either means step 4's fifth close condition is the reason (if any) the epic did not close, and the caller must not read `unknown` as "nothing was deferred or failed." A non-`unknown`, non-empty `FAILED-TO-FILE` is expected to shrink or clear on a later invocation without any user action, since step 1a retries it automatically; a non-empty `SKIPPED` will not, since it reflects a decision, not a failure.
